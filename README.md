# Billsplit

Разделение чеков между друзьями и учёт личных финансов.

- **Bill split:** фото чека → OCR → позиции → каждый участник группы отмечает, что брал → честный расчёт с налогом и чаевыми → долги и минимальный набор переводов. Чек может быть в любой валюте, долги считаются в валюте группы по курсу на дату покупки.
- **Друзья и группы:** заявки в друзья по email, личная ссылка-приглашение, ссылки-приглашения в группу (со сроком жизни и лимитом использований). В группу напрямую можно добавить только друга.
- **Расходы без чека:** аренда, такси, Airbnb делятся поровну, в процентах, точными суммами или по долям.
- **Возврат долгов:** кнопки «Pay with Venmo / PayPal / Zelle» по ник-неймам получателя. Погашение может отметить любая сторона: должник («я заплатил») или кредитор («получил»).
- **Финансы:** импорт выписки (CSV/OFX) → автокатегоризация → бюджеты, цели, дашборд в домашней валюте (правило 50/30/20, прогноз расходов, подсказки).
- **Инвестиции:** депозиты (ставка, капитализация, срок, ежемесячные пополнения, эффективная ставка, сумма к концу срока) и позиции в акциях/ETF/крипте/золоте по живым котировкам Yahoo Finance. Портфель в домашней валюте, история за год, доли, тренды рынка (S&P 500, Nasdaq, BTC, ETH, золото, USD/KZT, EUR/USD + свои тикеры). Калькуляторы: депозит, сложный процент с инфляцией и комиссией фонда, кредит (аннуитет и дифференцированный).
- **Совместный разбор чека в реальном времени:** когда несколько человек открыли один чек, отметки появляются у всех сразу без перезагрузки («Bob took Margherita», подсветка позиции), видно, кто ещё сейчас в чеке.
- **Капитал (net worth):** счета вручную (карты, наличные, сбережения, кредитки, кредиты, имущество) + инвестиции + долги с друзьями одной цифрой, ежедневная история и изменение за 30 дней.
- **Цели, привязанные к вкладу:** прогресс цели идёт от стоимости депозита/актива, для депозита — месяц, когда цель будет достигнута.
- **Прогноз на конец месяца:** фактический поток до сегодня + ожидаемые доходы/расходы по вашему паттерну за последние 3 месяца, баланс на последний день, ближайшие подписки.
- **Экспорт:** отчёт за месяц и отчёт по капиталу/портфелю в PDF (с графиками, кириллица) и CSV для Excel.
- **Подписки и регулярные платежи** определяются автоматически по выпискам (неделя/месяц/год). Накануне списания приходит напоминание.
- **Уведомления:** inbox в приложении и push через Expo: заявки в друзья, новый участник группы, чек распознан, «ты должен $X», погашение, скорое списание.
- **Клиент:** Expo (iOS, Android, Web из одного кода), см. [apps/mobile/README.md](apps/mobile/README.md).

## Архитектура

```
 iOS / Android / Web (Expo)
          │ HTTP/JSON  POST /billsplit.v1.<Service>/<Method>
          ▼
 ┌──────────────────┐  JWT, rate limit, CORS, request-id, лимит тела запроса
 │     gateway      │  grpc-gateway → gRPC; передаёт x-user-id бэкендам
 └──┬─────┬─────┬───┴──┐
    │gRPC │     │      │
  auth  social split  finance        ← каждый со своей схемой Postgres
    ▲     ▲ │ ▲  │ ▲     ▲ │
    └─────┴─┘ │  │ └─────┘ │          внутренние gRPC: UserDirectory, GroupDirectory, SplitInternal
              │  ▼ Kafka   ▼
              │ receipt.uploaded ──► ocr-worker ──► ocr (Python, RapidOCR)
              └──────── receipt.parsed ◄──┘        └► OCR.space (запасной)
                 receipt.finalized ──► finance (доля чека → личный расход)
                 statement.uploaded ─► finance (импорт выписки)
```

| Сервис | Что делает | Данные |
|---|---|---|
| `gateway` | единственная публичная точка входа (порт 8088) | — |
| `auth` | регистрация, логин, JWT, профиль и домашняя валюта, справочник пользователей | схема `auth` |
| `social` | друзья, группы, ссылки-приглашения | схема `social` |
| `split` | чеки, клеймы, сплит, долги, погашения, балансы | схема `split` |
| `finance` | транзакции, выписки, категории, бюджеты, цели, дашборд, подписки, напоминания | схема `finance` |
| `notify` | inbox уведомлений, push через Expo, устройства | схема `notify` |
| `ocr-worker` | распознавание чеков (Kafka consumer): RapidOCR → OCR.space → Claude vision | — |
| `ocr` | Python + RapidOCR (модели PaddleOCR на ONNX Runtime) | — |
| `web` | web-версия Expo-приложения (nginx) + `.well-known` для universal links | — |

Общий код лежит в `internal/platform`: конфиг, логгер (slog), метрики, Redis-кэш, Kafka, Postgres (пул, миграции по схемам, TxManager), gRPC-интерцепторы, rate limit, курсы валют.

Внутри каждого сервиса используется repository pattern: `repository.go` (интерфейсы + реализация на pgx), `service.go` (бизнес-логика), `grpc.go` (транспорт).

## API

Каждый метод вызывается как `POST /billsplit.v1.<Service>/<Method>` с JSON-телом. Контракты лежат в `api/proto/billsplit/v1`.

```bash
curl -s localhost:8088/billsplit.v1.AuthService/Register -d '{"email":"a@b.com","password":"password123","name":"Alice","currency":"USD"}'
curl -s localhost:8088/billsplit.v1.GroupService/ListMyGroups -H "Authorization: Bearer $TOKEN" -d '{}'
```

JSON-поля в camelCase, `int64` (все `*Cents`) приходят строками, `bytes` (фото, выписка) передаются в base64.

## Как устроены ключевые части

**Распознавание чеков.** `ocr-worker` получает `receipt.uploaded` и забирает фото у `split` по внутреннему gRPC (фото до 8 МБ в Kafka не кладём). Затем:

1. **RapidOCR** — свой сервис, бесплатно и без лимитов. Рамки с текстом группируются в строки по вертикали: «BANANAS … 1.96».
2. Эвристический парсер разбирает текст: UPC-коды, количество `2 AT 1 FOR`, скидки `1.00-`, SUBTOTAL/TAX/TOTAL, дату и магазин.
3. Если сумма позиций не сходится с SUBTOTAL и задан ключ, worker пробует **OCR.space** (25 000 запросов в месяц бесплатно). Перед отправкой фото сжимается до 1 МБ.
4. Если и это не помогло, а задан `ANTHROPIC_API_KEY`, вызывается **Claude vision**. Модель по умолчанию — `claude-opus-5-5`, её можно сменить через `ANTHROPIC_MODEL`. Ответ приходит строгим JSON по схеме, при отказе модели срабатывает серверный fallback. Это платный вариант, поэтому он стоит последним.
5. Из провайдеров выбирается самый «чистый» результат, он уходит в `receipt.parsed`. Если ничего не распозналось, плательщик вводит позиции вручную (`UpdateItems`) или создаёт чек сразу вручную (`CreateReceipt`).

**Мультивалютность.** Курсы ECB берутся из Frankfurter (бесплатно, без ключа, около 30 валют):

- Исторические курсы кэшируются в Redis на месяц, текущие на час.
- Если API недоступен, используется последний известный курс.
- Чек хранится в своей валюте. При финализации доли конвертируются в валюту группы по курсу на дату покупки.
- В финансах транзакции хранятся в исходной валюте. Дашборд конвертирует их в домашнюю валюту по курсу на конец месяца.
- «Кто кому должен» по всем группам показывается в домашней валюте.

**Инвестиции.** Депозит считается помесячно, как в банках: проценты начисляются по ставке/12 на баланс, капитализируются раз в период, пополнение приходит в начале следующего месяца, неполный месяц считается пропорционально дням (`internal/finance/deposit.go`; та же модель в `apps/mobile/src/lib/invest.ts` для калькулятора). Котировки (`internal/platform/market`) берутся из публичного chart/search API Yahoo без ключа и кэшируются в Redis (15 мин – 1 ч, последний удачный ответ хранится сутки как запасной). Котировки в пенсах (`GBp` и др.) переводятся в основную валюту.

**Реалтайм.** Сервис split после коммита публикует событие в Redis pub/sub (`rt:receipt:<id>`, пакет `internal/platform/realtime`). Gateway держит WebSocket `GET /v1/realtime/receipts/{id}?access_token=<jwt>` (доступ проверяется вызовом `GetReceipt` от имени пользователя), подписан одним `PSUBSCRIBE` на все чеки и раздаёт события своим сокетам; присутствие хранится в Redis sorted set, поэтому работает и с несколькими репликами gateway. Событие для клиента — сигнал «перечитай чек», источник правды остаётся в базе.

**Капитал, прогноз, экспорт.** Таблицы `accounts` и `net_worth_snapshots` (миграция finance 00008); снимок капитала пишется при открытии экрана и фоновой задачей раз в 6 часов. Прогноз (`internal/finance/forecast.go`) берёт средний день месяца за 3 прошлых месяца, масштабирует расходы по тому, как идёт текущий месяц, и не считает зарплату дважды, если она уже пришла. PDF собирается на сервере (`internal/finance/report`, go-pdf/fpdf + шрифт DejaVu Sans для кириллицы и ₸), CSV — с BOM, чтобы Excel открыл кириллицу.

**Сплит.** Вся арифметика в центах. Позиция делится по `shares`, налог и чаевые делятся пропорционально. Остаток центов раздаётся методом наибольшего остатка, поэтому сумма частей всегда равна итогу. Долги упрощаются жадным алгоритмом: не больше n−1 перевода.

**Валюты без копеек** (JPY, KRW, ISK…): все суммы хранятся в минимальных единицах своей валюты (¥1500 = 1500, $15.00 = 1500). Конвертация учитывает разницу знаков (`fx.Apply`), а `ListCurrencies` отдаёт `minorUnits`.

**Transactional outbox.** События пишутся в таблицу `outbox` той же транзакцией, что и данные. Relay переносит их в Kafka (`FOR UPDATE SKIP LOCKED`, работает при нескольких репликах). Если Kafka недоступна, события ждут в таблице, а не теряются.

**Безопасность**
- **Сервисный токен:** каждый внутренний gRPC-вызов несёт `x-internal-token`. Без него бэкенды отвечают `Unauthenticated` даже внутри docker-сети (проверено).
- **Отдельная роль Postgres на сервис** (`deploy/postgres/init.sql`): каждая роль владеет только своей схемой, чужие схемы и `public` недоступны, прав на создание схем нет (проверено: `permission denied for schema auth`).
- **Refresh-токены одноразовые:** при каждом Refresh выдаётся новый (хранятся в Redis). Повторное предъявление старого токена считается кражей и отзывает все сессии пользователя. Logout отзывает токен.
- **Rate limit в Redis** (token bucket на Lua) общий для всех реплик gateway. Если Redis недоступен, работает локальный лимитер.
- **JWT** проверяется только на gateway. Бэкенды получают `x-user-id` в metadata. Заголовки клиента gateway дальше не передаёт, поэтому подделать пользователя нельзя (проверено e2e).
- **Rate limit** — token bucket по IP. Для Register/Login/Refresh отдельный строгий лимит: 5 попыток, потом 429.
- **Пароли и логин:** bcrypt; на несуществующий email логин тратит то же время, что и на существующий (нельзя перебрать зарегистрированные адреса).
- **Ссылки-приглашения:** 128-битные случайные токены. Срок жизни и лимит использований проверяются под `SELECT … FOR UPDATE`.
- **Защитные ограничения:**
  - лимиты размера тела запроса и gRPC-сообщений;
  - таймауты на каждом уровне;
  - recovery от паник;
  - тип изображения проверяется по содержимому;
  - внутренние ошибки наружу не отдаются.
- **Наружу** открыт только gateway; остальные сервисы доступны лишь внутри docker-сети.

**Graceful shutdown** (`internal/platform/lifecycle`). Порядок остановки по SIGTERM:
1. readiness начинает отвечать 503;
2. 2 секунды дренажа, сервис ещё принимает запросы;
3. текущие HTTP- и gRPC-запросы доделываются;
4. Kafka-консьюмеры дообрабатывают взятое сообщение и коммитят его (остальные придут после рестарта, не попадая в DLQ);
5. outbox досылает события;
6. закрываются соединения.

Всё ограничено `SHUTDOWN_TIMEOUT` (25 секунд). Второй сигнал завершает процесс принудительно.

**Надёжность.**
- Двойная финализация чека невозможна: переход статуса защищён условием `WHERE status = PARSED`.
- Kafka: доставка at-least-once, все обработчики идемпотентны, 3 ретрая, потом DLQ (`<topic>.dlq`).
- gRPC-клиенты повторяют запрос при `UNAVAILABLE`.
- Если split недоступен, дашборд строится без блока долгов.

## Разработка

```bash
make tools proto   # protoc-gen-go, -go-grpc, -grpc-gateway и генерация
make test          # юнит-тесты
make test-integration  # интеграционные тесты на настоящих Postgres/Redis (testcontainers, нужен Docker)
make up / make down / make logs
```

CI (`.github/workflows/ci.yml`): `go vet`, юнит- и интеграционные тесты, проверка, что сгенерированный proto-код актуален, `tsc` + `eslint` + web-сборка фронтенда, сборка Docker-образов.
